### 正式指标评分（独立人工真值）

`evalkit.run_eval` 的规则评测用于内部回归；它不能证明专业正确性或真实适配效果。
正式 G2 指标只接受冻结的独立人工真值，并由离线评分器复算：

**Windows PowerShell**

```powershell
# 空模板是刻意不完整的错误路径：预期退出码 2，仍写出 JSON/Markdown。
$scorecardOut = Join-Path ([System.IO.Path]::GetTempPath()) ('agentedu-scorecard-' + [guid]::NewGuid())
py -3 -X utf8 -m evalkit.formal_scorecard --truth data/evaluation/formal_truth.template.json --out $scorecardOut
if ($LASTEXITCODE -ne 2) { throw "empty formal-truth template must be not_assessable" }
if (-not (Test-Path (Join-Path $scorecardOut 'scorecard.json')) -or -not (Test-Path (Join-Path $scorecardOut 'scorecard.md'))) { throw "scorecard reports were not written" }

# 仅在完成两名独立盲评和第三人仲裁后，使用同一命令把模板路径和临时目录替换为实际冻结真值文件与保存目录。
```

**Linux/macOS POSIX shell**

```bash
# 空模板是刻意不完整的错误路径：预期退出码 2，仍写出 JSON/Markdown。
scorecard_out="$(mktemp -d)"
python3 -X utf8 -m evalkit.formal_scorecard --truth data/evaluation/formal_truth.template.json --out "$scorecard_out"
test "$?" -eq 2 && test -f "$scorecard_out/scorecard.json" && test -f "$scorecard_out/scorecard.md"

# 仅在完成两名独立盲评和第三人仲裁后，使用同一命令把模板路径和临时目录替换为实际冻结真值文件与保存目录。
```

评分器对可评估的 `pass` 或 `fail` 返回退出码 0，对无效或不完整的
`not_assessable` 返回退出码 2。其公式、保守置信区间、输入门禁与信任边界见
[官方指标数学口径与验收](docs/官方指标数学口径与验收.md)；冻结、盲评、仲裁和

## 三、五个 Agent 与协同闭环

```
INIT → DIAGNOSE → PLAN → [ GENERATE(甲/乙双专家) → DEBATE → AUDIT
                            → (REVISE → AUDIT)* → ASSEMBLE ]* → READY
                                                                  ↓
                              READY → FEEDBACK → DECIDE → GENERATE …
```

| Agent | 职责 | 用不用大模型 |
|---|---|---|
| 学情诊断 | 前测作答 → BKT 估计掌握概率 → 盲区排序 | **不用**，只用它把数字翻译成人话 |
| 领域专家 甲 | 窄检索（知识点硬过滤 + top-k）起草断言 | 用 |
| 领域专家 乙 | 宽检索（查询扩展 + 重排）起草断言 | 用 |
| 交叉验证裁判 | 对齐两份断言，仲裁冲突，标注共识等级 | **不用** |
| 审核裁判 | 逐条断言核验，不过就打回 | 规则为主，模型为辅 |
| 决策调度 | 按作答正确率决定降维/巩固/进阶 | **不用** |

### 三条设计原则，建议整个项目守住

**1. 大模型只管生成内容，不管控制流。**

掌握度是算出来的，教学决策是规则判的。如果交给模型，同一份前测跑两遍结果
不一样，"个性化适配"和"动态迭代"就变成了看运气，评委随手试两次就露馅。

掌握度估计用的是 **BKT（贝叶斯知识追踪）**，不是答对率。答对率有两个硬伤：

- **蒙对算掌握。** 四选一蒙对概率 25%，答对率把这 25% 当成真会。
- **失误算不会。** 真懂的人手滑点错，答对率直接把他打成盲区。

BKT 用 `p_S`（失误率）和 `p_G`（蒙对率）显式建模这两件事，输出是掌握概率。
`p_G` 对四选一题的理论下界就是 0.25，不是拍脑袋的。初始概率 `p_L0` 由学历
和实操学时给先验，这就是榜题说的"整合先验知识画像"落到算法上的样子：
同样答对一题，有 120 小时实操的人比零基础的人更可能是真会。

参数现在用的是文献常用初值。**拿到真实作答数据后必须重新拟合**，
拟合时务必卡住 `p_S + p_G < 1`，否则模型退化，会出现"答错反而涨掌握度"的
荒唐结果（`core/bkt.py` 里的 `validate()` 会直接抛错拦住）。

**2. 没有引用的断言等于没说。**

生成 Agent 的最小输出单元是 `Claim`，每条必须带 `source_id`。审核不过就打回
重写，最多两轮，还不行直接丢弃。幻觉率能压住是因为架构上根本出不去，
不是生成完再去统计有多少条是错的。这是"技术创新性"那 25 分的核心论据。

**3. 检索按知识点硬过滤。**

生成某个知识点的资源时，模型只看得到该知识点的切片，跨知识点串味在检索阶段
就断了。这是压幻觉的第一道闸，成本几乎为零。

### 交叉验证与辩论：为什么不做"自由辩论"

榜题在创新性那一栏点名了"交叉验证与辩论"。这里**没有**让两个模型来回吵三轮，
那样烧 token、不可测、也不提准确率。做的是**断言粒度的对抗加仲裁**：

1. **两位专家独立起草。** 关键在"独立"：甲按知识点硬过滤取 top-k（窄而准），
   乙全库检索后按知识点重排（宽而全）。视角不同，犯的错才不同。
   两个 Agent 看同一份上下文，等于同一个模型问两遍，没有信息增益。
2. **对齐。** 按相似度配对，分三类：双方都提、仅一方提、双方冲突。
3. **仲裁。** 裁判不投票、不看谁说得漂亮，只回到知识库比证据。
   数值冲突走专门通道（见下），分差不够就两条都弃用。

**判"一致"必须同时满足三条：文本高度相似、出处相同、数值集合相同。**

第三条是单元测试逼出来的，也是整个机制里最关键的一行。原实现只看前两条，
结果甲说「限速250毫米每秒」、乙说「限速600毫米每秒」，文本相似度 0.95、
出处都是 KB-004，被判成"双方印证"直接放行。**数值篡改恰恰是文本最像的一类
冲突**，只看相似度等于把最危险的情形当成最可信的情形，方向完全反了。

对应地，仲裁分两层：数值集合不同时，以"谁的数字在知识库里"定胜负（黑白分明）；
其余情况才比整体证据分。

### 审核裁判的四层判据

大模型在垂直领域的翻车方式是有限几种，逐一对应：

| 失败模式 | 判据 | 代码位置 |
|---|---|---|
| 完全编造，不给出处 | 无 `source_id` 直接判无依据 | `_rule_check` |
| 引用了不存在的切片 | 切片 id 查不到 | `_rule_check` |
| 数字被改（250 写成 200） | 断言中的数字必须在切片中出现过 | `NUMERIC_STRICT` |
| 张冠李戴（把 A 的含义安到 B 的编号上） | 术语归属检查 + 全库最佳匹配比对 | `TERM_STRICT` / `MISATTRIB_MARGIN` |

第四类是开发时真被单元测试抓出来的：`报警SRVO-002含义为机器人超程` 这条
句式全对、引用格式也对，最初的覆盖率判据放行了它。补了两条规则才拦住。
这类错误人工审也容易漏，值得在答辩里单独讲一段。

接了真模型以后会多一层蕴含判断，但**上面四条规则始终并行跑，取更严的结果**。
不要用模型替掉规则，模型自己也会判错，两套独立判据一起用才有意义。

## 四、三种资源形态

三种形态共享同一个**已过审的断言池**，套三个模板产出：

- `lecture` 要点讲义，逐条带引用编号和出处
- `sop` 实操指南，前置条件 / 操作步骤 / 常见错误 / 安全提示
- `quiz` 分阶测试题，按难度排序，每题挂溯源

这样"至少 3 种形态"这条几乎不增加额外幻觉风险，也不用审三遍。要加第四种
（比如工艺卡、故障排查树），在 `GenerateAgent` 里加一个 `_xxx` 模板即可。

## 五、三项指标的口径（重要，答辩会被问）

### 先看这一条：知识库没核实，指标就不是效果指标

整套幻觉检测的逻辑是"断言必须被知识库支撑"。反过来，
**知识库本身如果是错的，审核闸只会把错误认证为正确**。
"幻觉率 0%"的真实含义是"生成内容与知识库一致"，**不是"内容正确"**。

早期演示基线中，26 条切片里有 21 条出处是编造的占位文本，
形如"《工业机器人操作与运维》第 4 章"，看上去毫无破绽 ——
这比明显胡编更危险，因为它会让人误以为内容有据可查。

现已联网核实：四个 FANUC 报警码（SRVO-001/002/005/062）与示教限速
250 mm/s 内容正确；围栏高度与安全距离属**出处错配**（数值挂在了一条
未经核实的国标条款名下）；其余 21 条标为待核实。**当前核实率 19%**。

每条切片现在都带 `verified` 字段，未核实的出处强制加"待核实·占位出处"前缀，
`run_eval` 按溯源可信度分层统计并在核实率不足八成时打印警告。

核实时记住一条：**单一网络来源不足以定案**。查 FANUC 报警码时就遇到
某服务商网站把 SRVO-001 说成"伺服放大器过载"，与多份官方资料矛盾。



阈值全部写在 `config.py`。**改这个文件要在 git 里留一次独立提交，提交时间
必须早于评测批次的时间戳。** 被问到"你这个 85% 怎么来的"，翻文件加提交记录。
规则先定后测，不是测完再凑定义，这一点守住了才叫科学定标。

### 当前跑分（50 组用例，注入率 30%）

| 配置 | 幻觉率 | 适配准确率 | 覆盖率 |
|---|---|---|---|
| 完整流程 | **0.00%** | 92.84% | 100% |
| 关闭审核 | 8.85% | 92.84% | 100% |
| 关闭辩论 | 0.00% | 92.84% | 100% |
| 两者都关 | 6.59% | 92.84% | 100% |
| 榜题目标 | <5% | ≥85% | ≥90% |

消融对照是最值钱的一栏。只报"我们幻觉率 0"没有说服力，报"关掉审核是 8.85%，
开着是 0%"才是能站住的因果论证。

### 辩论机制到底有没有用（这张表建议放进答辩）

关掉审核、只看辩论环节的分层统计（同一批 8952 条断言）：

| 共识等级 | 断言数 | 无依据条数 | 无依据率 |
|---|---|---|---|
| 双方独立印证 | 4899 | 27 | **0.55%** |
| 仅单方提出 | 4053 | 765 | **18.87%** |

**相差 34 倍。** 这说明"两位专家是否独立提出同一条"本身就是一个强幻觉信号，
交叉验证不是走过场。一条被编造出来的断言，另一位用不同检索视角的专家
几乎不会编出同一句。

这也解释了为什么"关闭辩论"那一行的幻觉率仍是 0：审核已经足够严，
辩论的价值不在于再降幻觉率，而在于**给每条断言标出置信等级**，
让下游可以对单方断言采取更保守的策略，也让资源里的溯源信息更有层次。

> **必须写进报告的限制：** 上面这组数是离线桩跑的，桩按种子给两位专家
> 注入不同的假事实，"独立编造不会撞车"在桩里部分是构造出来的。
> 真实模型下这个倍数会变，**接上真模型后必须重测**，不要把 34 倍当结论。

### 红队测试：拦不住的是哪一类

只报总体幻觉率，评委没法判断你是真解决了问题还是数据简单。
`python3 -m evalkit.redteam` 按幻觉类型分别报检出率：

| 类别 | 检出率 | 说明 |
|---|---|---|
| H1 凭空捏造 | 100% | 无出处，结构性堵死 |
| H2 引用悬空 | 100% | 切片不存在，结构性堵死 |
| H3 数值篡改 | 100% | 数值核验，含中文数字归一化 |
| H4 张冠李戴 | 100% | 术语归属 + 全库最佳匹配比对 |
| H5 过度泛化 | 100% | 对显式适用范围扩大做边界词核验 |
| H6 似真外推 | 100% | 对显式取消条件或步骤做边界词核验 |

对照 10 条真断言，**误伤 0 条**。

这里的 100% 只代表仓库内 21 条固定回归样本全部通过，不代表开放世界的
过度泛化和似真外推已经解决。规则只拦截证据中有明确限制信号的范围扩大、条件
取消；更隐蔽的语义变化仍需真模型 NLI 和人工抽查。修复前后明细与局限见
`docs/redteam_retest_2026-09-02.md`。

### 必须说清楚的局限

**适配那一项是自证的，别把它当效果指标。**

系统按预先登记的规则计算资源难度，这一项又用同一条规则去校验，
所以它必然接近 100%。它证明的是"实现与规则相符"，证明不了"规则本身合理"。

因此在所有对外材料里，这一项一律写作 **「适配规则一致性」**，不写"适配准确率"。
因此不得将规则评测的 100% 表述为“适配准确率”。评委会追问独立真值；
`run_eval` 在这一项跑到 100% 时会主动打印警告，防止它被误抄进 PPT。

> 自动化指标验证实现与预登记规则的一致性；适配效果由人工评分支撑，两件事分开写。

覆盖率同理偏结构性，但它有真信号：知识库缺切片的知识点会在这里掉下去。

这里有个真实的踩坑记录，值得写进方案文档：演示界面上线后，P-A 的首轮适配
只有 50%，而批量评测显示 92.84%。查下来是判定口径漏了一条约束 ——
**知识点本身有难度天花板**。「安全围栏高度不低于1.4米」是一级知识点，
学习者水平再高，这条知识也变不成三级内容；原判定不看天花板，
把这种无解约束记成"不适配"。批量评测按全部盲区平均，把它掩盖了；
演示只取前 4 个盲区（恰好都是低阶知识点），一下就顶了出来。
**小样本的可视化能暴露大样本平均值藏起来的规格 bug**，这条经验比修复本身有用。

**幻觉率同理，自动数只是筛子。**

`evalkit` 里的独立复核是在全库范围内做二元组匹配，和审核 Agent 的判据不同，
算是独立的第二次核验，但它仍然是自动的，抓不住语义层面的错。

### 队伍必须补的：人工标注

这是目前最大的缺口，也是"实用价值"那 30 分的真正来源。做法：

1. 从最终输出里随机抽 100 到 150 条断言（`evalkit/report/claims.json` 直接抽）
2. 两名同学**独立**标注「支持 / 不支持 / 无法判断」，标注前不许对答案
3. 算 Cohen's Kappa，一致性低于 0.6 说明标注标准没对齐，重新对齐再标
4. 分歧条目由第三人仲裁
5. 报告里同时给出：自动复核结果、人工标注结果、Kappa 值

适配准确率同样要人工评：抽 60 到 80 份资源，让 3 个人独立判"这份资源的难度
对这个学习者合不合适"，取多数。这才是评委认的数。

## 五点四、证据强度：点估计不足以下结论

四选一题答对 2 道，BKT 掌握概率 0.896，原实现判为"掌握牢固"。
但**纯靠蒙达到 2/2 的概率有 6.2%**——二十个人里就有一个能蒙出来。
3/4 判"掌握牢固"，蒙对概率 5.1%，同样站不住。

少量作答下的点估计本身就是高方差的。拿它当结论，
等于把"目前的最佳猜测"说成"已经确认"。

现在每个知识点除点估计外，同时给出两个数：

- **蒙对概率**：完全不会的人靠蒙达到该成绩的概率（二项分布右尾）。
  这是最直观的一个数，直接回答"我瞎蒙也能考成这样吗"。
- **可信区间**：作答正确率的 Beta 后验，按观测模型反解回掌握概率
  （这一步正是**扣掉蒙对成分**）。**下界才是能对外声称的下限。**

声称"已确认掌握"要同时满足三条：点估计过线、**区间下界也过线**、
蒙对概率不高于 5%。不满足则降级为"疑似掌握"并标注证据不足。

### 一个必须正视的结论

按这个门槛推算，**要确认掌握需要八题全对**（下界才过 0.80）。

这意味着**现在每知识点三道题的题库，结构上就不可能"确认"任何一个知识点**。
系统当前对所有知识点给出的都是"疑似掌握"或"证据不足"。
这不是模型效果问题，是题量问题。在题库扩到每知识点五到六道之前，
界面与报告一律写"疑似掌握"，不得写"已掌握"。

## 五点五、能力图谱：六维雷达

逐条列出十五个知识点没人读得进去。聚合成六个能力维度以雷达图呈现：
基础认知、现场操作、安全规范、精度标定、编程集成、运维调试。

雷达图很好看，因而特别容易骗人。三条设计压住这一点：

**轴不能太碎。** 不直接用知识点标签做轴——十三个标签里八个只覆盖一个知识点，
一道题的对错就能让整条轴塌掉，看着像能力图谱其实是噪声图。
归并到六维、每维至少三个知识点。

**必须画两层。** 外层点估计，内层区间下界，**两层之间的间隙就是"还不确定的部分"**。
只画点估计会让四题答对三题看起来和真正掌握一模一样。

**未测的维度不能画成零。** 零和"没测过"长得一样但含义相反：
前者是"确定不会"，后者是"不知道"。未测用虚线标出。

## 五点六、内容流水线：原始资料进，知识库出

以前往知识库加内容必须手写特定格式的 Markdown，而且 `kp` 字段必须填一个
**已经存在**的知识点编号 —— 这是个死循环：要加内容得先有知识点表，
而知识点表写死了 15 个。拿到一本真实手册想录进去，第一步就卡住。

现在反过来做：**先喂原始资料，让知识点从语料里长出来。**

```bash
python3 -m tools.ingest raw/                   # 切片、归类、质检，暂存
python3 -m tools.ingest raw/ --apply           # 确认后写入知识库
python3 -m tools.kb_audit                      # 交叉校验，查库内矛盾
python3 -m tools.kb_audit --quarantine         # 把冲突条目移进隔离区
python3 -m evalkit.factcheck_run               # 对外核实，出复核队列
```

支持 `.txt .md .pdf .docx .csv .tsv .xlsx`。PDF 按页读，位置标签带页码 ——
这是评委最可能要求当场翻的定位方式。

### 演示页的自定义入口与受控暂存

运行 `python3 server.py` 后，在线演示页除了三份合成画像，还可以接收一段
匿名的学习情况自述，先做自适应测评，再按本次实际作答生成诊断和资源。自述只
影响先验，不能替代答题证据；页面明确提示不要输入姓名、联系方式等个人信息。

页面也提供原始资料的**受控暂存**入口。它只接收 `.txt .md .pdf .docx .csv .tsv
.xlsx`，单文件最多 20 MiB，并要求填写来源/版本/授权说明和确认可使用。服务端会：

- 保存原始文件与文件指纹到本机 `data/incoming/`；
- 切片、归类、做质量门，把合格与隔离结果分别放入 `data/staged/uploads/<上传编号>/`；
- 生成包含来源说明的 `upload_manifest.json`，状态固定为 `pending_manual_review`。

这条入口**不会**调用 `--apply`，不会写入 `data/kb/`，更不会把任何条目标为
`verified=true`。`data/incoming/` 与 `data/staged/` 已被 Git 忽略。人工查看原文、
位置、隔离原因和外部证据后，才可针对单个原始文件执行正式摄入、库内冲突审计、
外部核实和人工确认。

### 三道关口，各查各的

| 工具 | 查什么 | 看不见什么 |
|---|---|---|
| `tools.ingest` | 摄入质量：乱码、目录页、无句读、重复 | 内容对不对 |
| `tools.kb_audit` | 切片**之间**是否自相矛盾 | 与外部资料是否一致 |
| `evalkit.factcheck_run` | 与**外部资料**是否一致 | 库内两条是否打架 |

第二道必须单独做。单条格式合规、出处也真实的两条切片可以互相打架 ——
同一个报警码在 A 页写"急停"、在 B 页写"过载"，两条都能过入库门禁，
外部核实也可能各自找到支持的来源。**只有放在一起比才能发现。**

这类矛盾的危害是隐蔽的：检索时两条都会被召回，生成的断言无论采信哪一条
都能通过审核（因为确实"有依据"），于是**幻觉率照样是零，而输出有一半是错的**。

### sourced 不等于 verified

摄入产出的状态是 `sourced`：出处是文件名加位置加文件指纹，可以回溯原文。
这与 `verified`（人工确认无误）是两回事 —— 出处真实只说明这句话确实印在
那本书上，不说明那本书是对的。

**但 sourced 本身已是巨大进步**：早期演示基线中的 21 条“《工业机器人操作与运维》
第 3 章"是查无此书，而 sourced 的切片可以当场翻给评委看。
`tools.ingest` 永远不写 `verified=true`，有测试盯着。

### 剔除靠隔离，不靠删除

自动剔除听起来干净，但删掉的是别人辛苦收集的资料。判据有误、阈值偏严、
误伤，都会导致内容悄悄消失而无人知晓。所以不合格条目一律移进隔离区
并写明原因。

冲突类问题还有一条特殊规则：**冲突双方中已核实的留下，未核实的隔离；
双方核实状态相同时两条都留下，只报告。** 第一版没有这条，
结果注入的错误数据把已核实的 KB-004、KB-017 一起带下水 ——
错误数据把正确数据挤出知识库，这是最糟糕的一种失败。

## 五点七、从早期演示基线到可交付版本：内容采集工具

早期演示基线与可交付版本之间差的是**内容**，不是代码 —— 26 条切片要扩到 300 条以上，
47 道题要扩到 90 道以上，还要补人工标注。这些只能由懂领域、
手上有真实资料的人来做。

**但可以把它从"手改 JSONL、错了没人知道"变成"有格式、有校验、有门禁"。**

### 知识库导入器

```bash
python3 -m tools.kb_import data/incoming/*.md          # 只校验
python3 -m tools.kb_import data/incoming/*.md --apply  # 校验通过后入库
```

输入是 Markdown，一条切片一个二级标题。选 Markdown 而不是 CSV，
是因为正文里逗号引号换行都很常见，CSV 转义出错就是静默截断。

**校验在入库时做，不在事后做。** 一条不合规的切片一旦进了库，
就会被检索到、被生成引用、被审核认证为"有依据"，
再想揪出来得翻整条链路；入口拦住只需要一次拒绝。

拒收项（error）：伪造出处、知识点不存在、长度越界、编号重复、
标了已核实却带待核实前缀。提醒项（warn）：约数措辞、观点措辞、
一条塞多个事实、与已有切片近重复。

最重要的是第一条：**未核实却给了看似真实的出处，直接拒收**。
一个像真的假出处会让所有人误以为内容有据可查，比明显编造更危险。

写这个工具时发现一个真问题：规范初稿写"切片 150 到 300 字"，
而**早期演示基线的 26 条切片全部落在 71 到 104 字，没有一条符合我们自己写的规范**。
改了阈值而不是改切片 —— 一个工业事实用中文讲清楚通常就是八九十字，
硬凑到 150 字只能靠注水，而注水的句子会拉低证据覆盖率，
反过来伤害幻觉检测。现在有测试盯着"阈值必须容得下现有语料"。

### 人工评分工具

```bash
python3 -m tools.rating sample --n 120 --raters 2   # 出盲评表
python3 -m tools.rating score --dir ratings/        # 汇总并算 Kappa
```

三项指标里"适配"那一项是自证的，幻觉率也只能证明"与知识库一致"。
**任何自动化检验都绕不开这层循环，因为判据和被判对象同源。**
打破循环只有引入一个与系统无关的判断源，也就是人。

工具不产生判断，只做三件事：抽样、去干扰、算一致性。三条设计：

- **隐藏系统结论。** 评分表里不出现难度值、掌握概率、共识等级。
  看到系统答案再打分，打出来的是对系统的认同度，不是独立判断。
  有测试专门检查评分表不泄漏这些字段。
- **打散顺序。** 每位评分者拿到的顺序不同，由固定种子决定，可复现。
- **低一致不取平均。** Kappa 低于 0.6 时工具会明确写出
  "请重新对齐标准后重标" —— 对不齐的两组数取平均只会得到一个
  看着精确的假数。

这和核实 Agent 是同一个思路：**机器造仪器，人出判断。**

## 六、学情访谈：把"预设"换成"现场"

早期版本只有三份写死的画像，点一下回放一遍。做得再好看，也还是一部片子 ——
评委看两眼就知道数据是喂进去的。而且榜题创新性那条明确要求
**"动态追问与启发式交互导学，打破静态资源单向输入局限"**，光靠预设画像
根本没碰到这个要求。

现在的主路径是：**自述 → 自适应测评 → 现场诊断 → 生成资源**，全程可交互。

### 1. 自述解析

学习者打一段话，抽出学历、阶段、方向、实操学时。有模型走模型再用规则校验，
没模型纯规则跑，离线一样能用。

抽取结果**只用来给 BKT 的初始掌握概率定先验，不直接决定结论**。
先验会随作答证据累积被冲淡，所以抽错了也不会一错到底 —— 自述是主观的，
学习者容易高估或低估自己，不能让它拍板。

规则里踩过的坑：「高职电气自动化**二年级**」曾被算成"两年工龄"，
折合 3200 小时实操，先验直接顶到上界，测评开局就问偏。学制和工龄要分开。

### 2. 自适应选题

不是把 47 道题一股脑发下去。每次只发一道，按信息量挑下一道：

    P(答对) = p_L·(1-p_S) + (1-p_L)·p_G

P 越接近 0.5 信息量越大 —— 有把握答对或答错的题，问了也没告诉你新东西。
所以挑 |P − 0.5| 最小的，再叠一个"该知识点问得越少越优先"的权重。

### 3. 动态追问

作答与已有证据冲突时，就地追加同知识点的一道题：

| 情形 | 歧义 | 动作 |
|---|---|---|
| 估计已掌握（≥0.65）却答错 | 是失误还是真不会 | 追问一次 |
| 估计为盲区（≤0.35）却答对 | 是真会还是蒙对 | 追问一次 |

BKT 的 `p_S`（失误）和 `p_G`（蒙对）正好把这两件事显式建模了，所以歧义可以量化，
追问不是随便加一道，是**为了消解特定歧义**而加。

这里有个必须记的坑：最初没限制追问的触发前提，结果先验偏低（零基础学员 0.20）时，
**任何一道答对都满足"估计为盲区却答对"，第一题就触发追问**。
但那时手上一条证据都没有，所谓冲突是跟一个通用先验冲突，消解不了任何歧义。
实测 16 题里有 7 题是追问，覆盖率被吃掉近一半。
修法是加一条门槛：**该知识点必须已有作答证据**才允许追问。

### 4. 前置推断

15 个知识点各测到可信度 0.75 需要每点 3 题、合计 45 题，没有学习者愿意答。
所以加了一条：**前置已确认是盲区的知识点，不再实测，直接推断为盲区**。
连坐标系都分不清的人不可能会 TCP 四点标定，花一道题确认这件事是浪费。

推断出来的盲区在界面上用虚线框标出，**不冒充实测结果**，报告里也要分开统计。

### 5. 单一在线执行链

`web/index.html` 只负责输入与展示，检索、BKT、自适应选题、辩论仲裁、
审核规则和资源组装统一由 Python 后端执行。项目不再维护浏览器端的第二套算法，
避免两套实现和两套数据源随迭代发生漂移。

## 七、让大模型当主考官

题库只有 47 道，每个知识点 3 道，难度档位就那么几级。学习者水平落在两道题
之间时，只能拿一道偏难或偏易的凑合 —— 太难必错、太易必对，那一问的信息量白费。

所以让模型进来做三件事：**读自述做判断、按需现场命题、综合出诊断**。

### 先说风险，这条比什么都重要

**模型出题 = 模型定义"正确答案"。这是本项目里后果最重的一类错误。**

讲义里写错一句，学习者可能看出来，审核也拦得住。但答案标错了，
系统会**拿一把错的尺子去量人**：

- 学习者答对却被判错 → 掌握度往下走 → 系统给他推更简单的内容
- 学习者答错却被判对 → 盲区被漏掉 → 该补的没补

错误不停在一句话上，而是灌进学情模型，决定后面所有资源。
学习者还没法申诉 —— 他不知道标准答案是编的。

所以规矩是：**生成题必须过闸，一道都不例外；过不了就丢，回退题库。
宁可用一道糙题，不能用一道错题。**

### 四关审核（`ExaminerAgent.vet`）

| 关 | 查什么 | 为什么 |
|---|---|---|
| 1 | 正确答案被所引切片支撑 | 沿用 `AuditAgent` 那套判据，不给命题开小灶 |
| 2 | 每个干扰项都**不**成立 | 一题两解比答案错了还糟，且没有环节会发现 |
| 3 | 题干不含切片以外的数值 | 只查题干，**不查选项** |
| 4 | 选项不重复、无长度线索 | 最长的恰好是答案，学习者不会也能蒙对 |

几处踩过的坑，都留在代码注释里了：

**数值型选项不能用文本覆盖率判。** 「0.5」这种纯数字选项，分词后是
`["0","5"]`，只要正文里任意位置出现过 0 和 5，覆盖率就是 1.00，判据完全失效。
数值型的正确判据是"这个数在不在知识库里"，黑白分明，不该绕道文本相似度。

**关 3 只查题干不查选项。** 干扰项按定义就该带知识库里没有的数，
拿这条去卡选项等于禁止出错误选项 —— 第一版就是这么把所有题都毙掉的。

**长度线索规则跳过纯数值选项。** 「10000」比「2」长，但没人会因此认为它是答案。

**干扰项审核要能看见否定。** 这是最隐蔽的一个。安全和规程类内容里，
**最好的干扰项恰恰是手册明令禁止的做法**：KB-017 写「切勿在未按住解除按钮时
强行驱动」，那「直接强行反向驱动」就是标准干扰项 —— 可它跟切片的二元组覆盖率
高达 0.60，被判成"可能也对"直接毙掉。二元组重合看不见否定，
「强行驱动」和「切勿强行驱动」在词面上几乎一样。

照这么卡下去，模型只能去造一眼假的干扰项（「更换伺服电机」），题目区分度就废了。
修法是把切片**按分句**切开，比较选项跟"禁止句"和跟普通正文的重合度，
更像禁止句就放行。用比较而不是绝对阈值，因为干扰项通常只借用禁止句的一部分措辞
（那句只有 0.40），卡 0.5 会漏、卡 0.3 又会误判。

反向保护：选项**自己**带禁止词说明它在复述规则、本身成立，不享受豁免。
切分粒度也必须到分句 —— 「加注时必须打开排脂口，禁止在封闭状态下加注」
只按句号切会把整句当禁止句，连正确做法都被判成"被禁止"，
等于把正确答案塞进干扰项。

### 生成题的难度是"要求的"，不是"实测的"

题库题的难度标签背后有出题人的判断，生成题没有任何作答数据可标定。
所以生成题带 `level_source: "requested"`，题库题是 `"bank"`，
**这个标记一路带到界面和报告里**。

为什么较真：难度会喂给自适应选题。拿一个未经标定的数当真，
等于用没校准的尺子挑下一道题。真正的标定需要积累作答数据后做项目分析，
这一项排在待办里。

### 统计口径

`ExaminerAgent` 把三个数分开记，**不要合成一个"通过率"**：

- `requests` 命题请求次数
- `rejects` 被四关拒收（**闸门在起作用的证据**）
- `no_output` 模型没给出可解析的题（模型或提示词的问题，与闸门无关）

混成一个数报出来，等于把闸门的功劳和模型的短板搅在一起，
答辩被问"你们到底拒了多少道"就答不上来。报告里建议直接给这三个数。

### 综合诊断：数字一律不交给模型算

掌握概率、盲区、可信度、作答模式全部由规则算好再传进去，模型只做归纳表述。
这样报告读起来是自然语言，但每个数都可复算，被追问时能当场翻出来源。

`_patterns()` 里的规则统计是给模型的原料，也是可核验的证据链，包括：
难度断层（基础稳、进阶崩 = 记忆到应用没转化）、安全类专项正确率、
追问触发次数、样本不足的知识点。

命题、自述分析和综合诊断统一通过 `server.py` 接入模型；前端不接触 API Key。

## 八、题目质量：题不好，尺子就不准

命题闸门（`agents/examiner.vet`）管的是"题**对不对**"。
`core/itemquality.py` 管的是另一件事：**题好不好用**。

两者不能互相替代。一道题可以完全正确、出处清楚、干扰项都不成立，
却仍然测不出任何东西：太简单人人都对、干扰项一眼假、两个干扰项几乎一样。
这些不是错题，闸门放它们过去是对的 —— 但拿它们估掌握度，
BKT 的蒙对率 `p_G` 就不再是 0.25，估出来的掌握概率整体偏高，且偏多少不知道。

```bash
python3 -m evalkit.itemreport      # 出题库质量报告 + 待改清单
```

### 上线第一天就抓到两个真问题

**其一：47 道题里 38 道答案在 B。** 一路选 B 能得 81 分，
整套测评的测量效力等于零。这是我们自己手写的题库，写的时候谁也没注意。
已用确定性置换打散（同时把三份画像里存的作答下标一并重映射，
否则对错模式会静默改变，得到一批"通过但含义已变"的测试，最难查）。
现在有 `test_real_bank_is_balanced` 盯着，再偏就红。

**其二：所有判断题的答案都是「正确」。** 这个更糟 —— 位置偏斜至少还有
25% 的蒙对下限，答案全同是 100%。根因是题干由已过审的断言直接生成，
自然全是正命题。

修法有点意思：**把审核闸反过来用**。扰动断言里的数值或特征术语，
再送回 `AuditAgent`，**只有被判为 contradicted 才采纳**。
也就是说这条假命题的"假"是知识库认证过的，不是我们自己认为它假。
认证不了就不产出反向题 —— 宁可少一道，不能放一条自己也说不清真假的说法进去。
现在真假比是 8:4，Python 与浏览器端一致。

### 结构检查（不需要作答数据）

| 代码 | 查什么 | 为什么 |
|---|---|---|
| LENCLUE | 正确答案明显更长 | 应试技巧就能蒙对 |
| CATCHALL | 「以上都对」这类兜底项 | 把题变成逻辑推理，测的不再是本知识点 |
| ABSOLUTE | 干扰项绝对化措辞 | 「所有」「绝不」会被直接排除 |
| DUPDISTRACT | 两个干扰项几乎一样 | 名义四选一、实际三选一，`p_G` 失准 |
| FARDISTRACT | 干扰项离题 | 一眼能排除，白占选项位 |
| SHORTSTEM | 题干过短 | 缺少作答语境 |

阈值有个标定细节：判重复用 0.60 而不是直觉上的 0.8。中文短选项用二元组
Jaccard 时，改一个字就掉两个二元组 —— 「由三个直线轴构成」和
「由三个直线轴组成」实际是同一个选项，相似度却只有 0.667；
而真正不同的两个干扰项是 0.304。两档之间间隔够大，0.60 落在中间。

### 实测标定（需要作答数据）

- **难度 p 值**：答对比例。注意方向 —— p 越大题越**简单**，容易读反。
- **区分度（点二列相关）**：答对这道题的人，整份测评是不是也考得更好。

区分度是**发现答案标错的唯一可靠手段**，对本项目尤其要紧：
生成题的答案是模型断言的，标错了不会有任何环节报错。一旦标错，
水平高的人反而更容易选到真正正确的那个选项、被判为错，
于是相关系数**变成负数**。

| 区分度 | 判断 |
|---|---|
| > 0.30 | 良好 |
| 0.15 ~ 0.30 | 可用 |
| 0 ~ 0.15 | 几乎不提供信息 |
| **< 0** | **优先怀疑答案标错**，而不是题目难 |

模拟验证：一道答案标错的题，区分度 **-0.149**，直接判为不可用。
样本少于 8 个时返回 `None`，不给一个假装精确的数。

## 十二、常见问题

**Q：为什么不用 LangGraph / AutoGen？**

骨架阶段手写状态机有三个好处：每条状态转移边都能直接写成单元测试（榜题点名
要求测协同调度逻辑）；出问题时栈很浅，学生自己 debug 得动；状态和事件是自己
定义的，前端可视化和评测中间数据可以复用同一份。真需要并行调度或人在回路
再迁，接口留好了。

**Q：为什么不用 jieba / faiss / sentence-transformers？**

目标是"评委机器上 clone 下来直接 `python3 cli.py` 就能跑"，少一个依赖少一个
现场翻车的可能。二元组 BM25 在几百到几千切片的规模上召回够用，瓶颈不在这里。
要升级只需替换 `Retriever.search`，接口不变。

**Q：`AGENTEDU_INJECT` 是干什么的？**

离线桩的幻觉注入率，`0.3` 表示三成的生成批次会被塞进一条假事实。**仅用于
测试和演示**，用来验证审核 Agent 真的拦得住。正式跑分时设为 0 或不设。

**Q：审核把正确的内容也拦了怎么办？**

调 `config.EVIDENCE_MIN`。调低会放进更多东西，调高会误伤。改之前先跑
`python3 -m unittest tests.test_audit -v`，那里的四类夹具就是防止调过头的护栏。
真误伤了，正确做法通常是补切片而不是放松阈值。
