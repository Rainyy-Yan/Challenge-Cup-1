# 知识库切片规范

扩充知识库时照这个写。知识库是整套方案里最大的杠杆，也是唯一没法靠代码
偷懒的部分。26 条只是示范量级，实际要做到 300 条以上。

---

## 一、格式

`data/kb/*.jsonl`，一行一条，UTF-8，无 BOM。

```json
{"id": "KB-027", "kp": "KP-03", "title": "工具坐标系与用户坐标系的区别", "source": "《工业机器人操作与运维》第4章", "text": "工具坐标系以工具中心点为原点……"}
```

| 字段 | 要求 |
|---|---|
| `id` | 全局唯一，`KB-` 加三位数字，按录入顺序递增，**永不复用** |
| `kp` | 必须是 `knowledge_points.json` 里已存在的知识点 id |
| `title` | 一句话说清这条讲什么，会参与检索，别写"知识点3"这种废话 |
| `source` | 具体到章节或文件版本号，答辩要能当场翻到。未核实的必须带「【待核实·占位出处】」前缀 |
| `verified` | 布尔值，是否核实过来源。**不允许缺省**，见第一点五节 |
| `source_note` | 可选。出处存疑或错配时写明原委 |
| `text` | 正文，见下面的写法要求 |

`id` 永不复用这条要守死。断言里存的是 `source_id`，复用 id 会让历史评测
数据全部对不上，返工代价极大。作废的切片改 `text` 为空并加 `"deprecated": true`，
不要删行。

---

## 一点五、核实状态：本项目最要紧的一个字段

每条切片必须带 `verified` 字段，取值只有 `true` 和 `false`，**不允许不表态**。

### 为什么这件事压倒一切

整套幻觉检测的逻辑是"断言必须被知识库支撑"。
那么，**如果知识库本身是错的，审核闸只会把错误认证为正确**。

跑分里的"幻觉率 0%"，真实含义是「生成内容与知识库一致」，
**不是「内容正确」**。这两句话差得很远，而所有对外材料都极容易把前者说成后者。

### 两条硬规则

**未核实的切片，出处必须带「【待核实·占位出处】」标记。**

这一条防的是最危险的情形：一个看起来像真的出处 ——
比如"《工业机器人操作与运维》第 4 章" —— 会让读者、评委、
甚至团队自己误以为内容有据可查。骨架版交付时 26 条切片里有 21 条就是这样，
出处全是编的，而内容看上去毫无破绽。这比明显编造更隐蔽，也更危险。

**出处错配要留说明，不能悄悄改掉。**

KB-022 原稿把围栏高度与安全距离挂在 GB 11291.2-2013 名下。
内容也许合理，但把具体数字挂到一条没查证过的标准条款上属于出处错配 ——
它有一个真实存在的标准号做掩护，比凭空编造更难被发现。
这类切片改的时候要在 `source_note` 里写明原委，供后续复核。

### 能不能让模型自动核实

能，但有一条铁律，破了就前功尽弃：

**模型的判断本身永远不能成为核实依据。核实依据只能是外部证据。**

直觉做法是把切片丢给大模型问"这条对不对"，模型说对就标成已核实。
**这么做比不核实还糟。** 知识库本来就是大模型写出来的，
再让大模型判它对不对，等于让同一个来源自己给自己背书 ——
模型倾向于认可符合自己先验的说法，而那些说法恰恰是它自己生成的。
结果是把"未核实"洗成"已核实"，标签变了、可信度一点没变，
错误从此戴上一顶合规的帽子，比裸奔更难被发现。

`agents/factcheck.py` 按这条铁律实现。模型在其中只干两件事：
把切片改写成检索词；读取**检索回来的外部资料**判断是否支持该切片。
第二件事仍是判断，但判断对象是别人写的资料，不是自己的记忆。
检索不到资料就判"存疑"，**绝不允许回落到模型记忆**。

状态取值分五档，其中最后一档机器永远不能写：

| 状态 | 含义 | 谁能写 |
|---|---|---|
| `unverified` | 未核实（默认） | 机器 |
| `machine_checked` | 找到外部证据且多来源一致 | 机器 |
| `disputed` | 证据不足、来源单一、或多来源矛盾 | 机器 |
| `refuted` | 找到明确矛盾的外部证据 | 机器 |
| `verified` | **人工确认无误** | **只有人** |

最后一行是整个设计的支点。一旦机器能写 `verified`，
整条溯源链就退化成"模型说它查过了"，与不核实无异。
`apply_results()` 里有断言直接拦住这种写入。

三条判定规则：

- **多来源**：至少两个互相独立的**域名**一致才判 `machine_checked`。
  同一域名下的多个页面不算独立来源。
- **矛盾优先**：只要有一个来源给出矛盾结论，就判 `refuted`，
  哪怕支持方更多。测试里构造过 3 比 1 的场景，矛盾方胜出。
  这一条对应真实案例：某服务商网站把 SRVO-001 说成"伺服放大器过载"，
  与多份官方资料矛盾，当时是人发现的，现在系统能自动顶出来。
- **无证据不放行**：检索源没接上时全部判存疑。这是正确行为不是故障。

用法：

```bash
python3 -m evalkit.factcheck_run              # 出人工复核队列
python3 -m evalkit.factcheck_run --apply      # 把机器状态写回知识库
```

接检索源在 `evalkit/factcheck_run.py` 的 `build_search()` 里，
实现 `SearchBackend` 接口即可，可以用模型自带的联网工具、
独立搜索 API 或企业内网检索。

**这个工具是省人力的，不是替人拍板的。** 它把证据摆到你面前并排好优先级，
最后那一下还得人来点。检索到的网页本身也可能是错的。

### 核实到什么程度算数

| 级别 | 标准 | 可否标 verified |
|---|---|---|
| 一手 | 厂商官方手册、国标原文、行业标准原文 | 可以 |
| 二手交叉 | 三份以上互相独立的资料说法一致 | 可以，出处注明「多方资料一致」 |
| 单一网络来源 | 一篇博客、一个问答帖 | **不可以** |
| 记忆或推断 | "我印象里是这样" | **不可以** |

第三条尤其要守。核实 FANUC 报警码时就遇到过：
一份维修服务商的页面把 SRVO-001 说成"伺服放大器过载"、
SRVO-002 说成"过电压"，与多份官方手册摘录完全矛盾。
**单一来源不足以定案**，这不是理论上的顾虑。

### 当前状态

骨架版 26 条切片中，已核实 5 条（四个 FANUC 报警码 + 示教限速 250 mm/s），
其余 21 条全部标为未核实。核实率 19%。

`python3 -m evalkit.run_eval` 会把断言按"落在已核实切片"与
"落在未核实切片"分层统计，并在核实率低于 80% 时打印警告，
明确写出这些数字属于系统自检、不得作为答辩举证。

**扩充知识库时，把核实和录入当成同一道工序**，
不要先录三百条再回头补核实 —— 那时没人分得清哪条查过哪条没查过。

## 二、正文怎么写

### 长度

**80 到 200 字**，硬性下限 60、上限 400。

这组数字被现实修正过。规范初稿写的是 150 到 300 字，
但写完导入器一测才发现：**骨架版 26 条切片全部落在 71 到 104 字，
没有一条符合我们自己写的规范**。

两种改法 —— 把切片写长，或者把阈值改对。选了后者，理由是
"一条切片只讲一件事"这条更根本：一个工业事实（一个报警码的含义、
一条公差要求）用中文讲清楚通常就是八九十字，硬凑到 150 字只能靠注水，
而注水的句子会拉低审核的证据覆盖率，**反过来伤害幻觉检测**。

- 短于 60 字，上下文不足，模型容易脑补
- 长于 400 字，一条切片里塞了多个事实，审核时无法定位到底哪句有依据

一段讲不完就拆成两条，用 `title` 区分，别硬塞。

### 一条切片只讲一件事

反例（错的）：

> 示教器有三位使能开关，运行模式分T1/T2/AUTO，另外坐标系分关节、直角、工具三种，
> TCP标定用四点法……

这条正文里有四个独立事实，分属两三个知识点。审核 Agent 判定"这条断言有没有
依据"时会一片混乱，覆盖率统计也会失真。

正例：拆成四条，各自挂到对应的 `kp`。

### 数字必须写全，不要写约数

审核有一条硬规则：**断言里出现的数字，必须在所引切片里出现过**。

所以切片里写"速度限制在250毫米每秒以内"是对的，写"速度有严格限制"就等于
把这个数字从知识库里删掉了，后面模型再生成带数字的内容一律会被拦。

单位、公差、周期、层数上限，凡是有具体数值的，一个都别省。

### 保留原始术语和型号

`SRVO-062`、`MOVJ`、`GB 11291.1-2011` 这类要原样写。检索的分词逻辑对
字母数字组合做了保护，型号能被完整命中。改写成"某报警代码"会同时毁掉检索
和审核。

### 不要写观点和推荐

切片里只放**可核验的事实**。"建议优先选用 MOVJ 以缩短节拍"这种是可以的，
因为它出自手册；"我们认为这个方案更好"不行。

判断标准：这句话能不能在原始资料里指出出处。不能就不写。

## 三、优先补哪些内容

按对指标的贡献排：

### 1. 封闭事实集（最高优先级）

报警代码表、指令参数表、公差要求、周期规定、标准条款编号。

这类内容的特点是**对错一查便知**，是幻觉率能有 ground truth 的唯一来源。
人工标注的时候标注员不用争论，直接查表。

工业机器人这个领域里，建议至少覆盖：

- 常见报警代码 40 条以上（含义 + 处理步骤）
- 运动指令与参数 20 条以上
- 国标条款要点 15 条以上（GB 11291.1、GB 11291.2）
- 保养周期与公差表 10 条以上

### 2. 操作流程（SOP 资源的原料）

带明确步骤顺序的内容。写的时候把步骤序号留在正文里，生成的实操指南会更像样。

### 3. 常见错误与故障现象

"如果不做 X 会导致 Y"这类因果陈述。这是实操指南里"常见错误"那一节的原料，
也是最能体现"贴合行业实际"的部分。

### 4. 概念解释（优先级最低）

模型本来就会，补进去边际收益小。除非你的领域有和通识冲突的特殊定义。

## 四、覆盖率自查

每加一批切片，跑一次：

```bash
python3 -m unittest tests.test_core.TestRetrieval -v
```

其中 `test_every_kp_has_at_least_one_chunk` 会检查有没有空知识点。**知识点表
里有、知识库里没切片的知识点，会直接把覆盖率指标拉下来**，这一项是三个指标里
唯一有真信号的，别在这里失分。

目标是每个知识点至少 8 到 15 条切片。15 个知识点乘 15 条就是 225 条，再加上
交叉引用的内容，300 条是个合理量级。

## 五、版权与来源

用于比赛提交的知识库切片，注意：

- 教材和手册的**原文大段照抄有版权风险**，提交材料里建议以自行改写的技术要点
  为主，`source` 字段标明依据的资料
- 国标条款要点可以引用，标注标准号和条款号
- 企业内部资料要取得授权，没授权就别放进提交包
- 每条切片的 `source` 要能对应到一份真实存在、评委能查证的资料

榜题总则里有一条：参赛者须对参赛作品拥有完整独立知识产权，无权属纠纷。
知识库是最容易出问题的地方，早点处理。

## 六、分工建议

知识库是纯体力活，但不能外包给不懂的人。建议：

- 1 人定切片边界和 `kp` 归属（要懂领域）
- 2 人录入正文（照规范抄写改写）
- 定切片边界的那个人**逐条复核** `kp` 归属，归属错了检索的硬过滤就失效了

一条切片熟练后大概 5 到 8 分钟。300 条约 30 小时，两个人分摊一周内能干完。
第 1 周就要启动，拖到第 3 周一定来不及。
