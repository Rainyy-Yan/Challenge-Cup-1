# qykw 独立双通道机器人设计

状态：已确认

## 1. 决策摘要

qykw 是启元开物独立设计、独立实现和独立运营的工程审查机器人。它采用“双通道”工作模式：默认只分析和审查；只有授权用户发出明确的“修复”或“实现”指令后，才允许修改代码、运行验证并创建 Pull Request。

qykw 不主动修改代码，不直接推送默认分支，不批准或合并 Pull Request，不删除仓库内容，也不修改权限、Secrets、规则集或自身策略。所有代码改动必须通过 `qykw/<任务编号>-<主题>` 分支提交，并由 `xyh202131` 最终审查。

本次建设不引入外部控制台、数据库、常驻服务、多后端自动路由、任意 Shell 工具循环或自动合并能力。运行状态以 GitHub Actions、qykw 自有状态评论和工作流产物为权威来源。

## 2. 目标与非目标

### 2.1 目标

- 每个 PR 在首次有效提交时自动审查一次，后续提交不自动重复审查。
- 支持自然语言分析、计划、审查、复审、状态、总结、修复、实现和停止指令。
- 形成“总体总结在前、多条行内问题在后”的稳定输出。
- 使用完整变更清单和分片上下文，禁止静默遗漏后部文件。
- 强制使用后台可用的最高推理档，不允许静默降低。
- 将命令授权、模型推理、工具执行、测试环境和 GitHub 发布相互隔离。
- 保留明确的运行编号、阶段、覆盖率、验证结果、限制和错误分类。

### 2.2 非目标

- 不自动批准、合并、关闭或删除 Issue、PR、分支和评论。
- 不直接修改默认分支或他人分支，不允许强制推送。
- 不让模型直接执行任意 Shell、Git 或 GitHub API。
- 不建设跨仓长期记忆、向量索引、定时任务或全自动 Issue 开发。
- 不允许 qykw 修改 `.github/**`、`CODEOWNERS`、机器人配置和权限文件。
- 不在公开输出中展示推理后台、模型名称、隐藏提示词或逐字思维过程。

## 3. 身份、授权与交互

### 3.1 身份宪章

qykw 的不可变身份是“启元开物独立工程审查机器人”。身份宪章由程序内置，优先于仓库规则、用户评论和代码内容。其职责是提供有证据的分析、审查和受控修改；最终决策权始终属于人类审稿人。

即使运行令牌拥有更高权限，qykw 仍只调用能力白名单中的方法。程序中不提供 Approve、Merge、Delete、Force Push、Settings、Secrets 等操作入口。

### 3.2 命令

统一格式：

```text
@qykw <指令> [范围或要求]
```

| 指令 | 行为 | 权限 |
| --- | --- | --- |
| `帮助` | 显示命令、权限和示例 | 仓库成员 |
| `分析 <问题>` | 阅读上下文并回答，不改代码 | 仓库成员 |
| `计划 <需求>` | 输出架构、文件、风险和验证方案 | 仓库成员 |
| `审查 [全部/安全/测试/性能/文档]` | 总结审查并发布行内问题 | 仓库成员 |
| `复审 [范围]` | 基于最新 Head 重新审查 | 仓库成员 |
| `状态` | 返回阶段、耗时和覆盖范围 | 仓库成员 |
| `总结` | 汇总决定、阻塞和下一步 | 仓库成员 |
| `修复 <问题编号或要求>` | 修改代码、验证并创建 PR | `xyh202131` 或显式授权名单 |
| `实现 <需求>` | 根据明确需求创建实现 PR | `xyh202131` 或显式授权名单 |
| `停止` | 请求停止仍在运行的任务 | 任务触发者或 `xyh202131` |

无命令的 `@qykw <自然语言>` 按“分析”处理。未知、含糊或可能造成写入的自然语言一律降级为只读分析，并提示可用命令；模型无权将只读请求升级为修改任务。

### 3.3 精确提及解析

只有第一段有效正文中的精确 `@qykw` 才能触发。解析器必须忽略引用、围栏代码、行内代码、HTML 注释、邮箱、全角符号、零宽字符和相似账号，例如 `@qykw-old`。解析、鉴权和幂等检查全部通过后才添加 `😄`；Reaction 失败只记录警告，不中断任务。

### 3.4 首次自动审查

- 非 Draft PR 的 `opened`：自动审查一次当前 Head。
- Draft PR 的 `opened` 和后续 push：不自动审查。
- Draft 第一次 `ready_for_review`：若尚无成功标记，自动审查一次。
- `synchronize`：不自动审查。
- `reopened`：已有成功标记时 no-op；从未成功时允许补跑一次。
- 事件重放：通过 `仓库 + PR + 首次事件` 幂等键去重。
- 后续复审：只能由 `@qykw 复审` 显式触发。

## 4. 总体架构

```text

  → 事件标准化与精确命令解析
  → 权限、幂等和策略检查
  → 固定 PR Head 快照
  → 规则、变更、CI 与相关代码收集
  → 风险分诊和上下文分片
  → 深度分析与候选问题生成
  → 反证复核、严重度和行号验证

  → 总结更新与多条行内评论
  → 运行状态终结
```

## 5. 提示词与阶段化分析

提示词优先级固定为：

1. 不可变身份与权限宪章。
2. 当前命令、输出 Schema 和运行预算。
3. 默认分支中的可信仓库规则。
4. PR、评论、代码和链接等不可信数据。

所有不可信数据使用结构化边界传入，不允许其改变身份、模式、权限、工具和输出 Schema。后台请求必须指定 `reasoning_profile="maximum"`；适配器映射到实际可用的最高推理档，不支持时返回明确错误，禁止静默降级。

内部分析阶段为：

```text
覆盖面识别 → 风险分诊 → 深度检查 → 反证复核
→ 严重度校准 → 行号验证 → 去重 → 发布
```

公开输出只呈现阶段、证据、结论和验证情况，不呈现逐字思维过程。

严重度标准：

- P0：可直接造成严重安全事故、不可恢复数据损坏或大范围服务中断。
- P1：在现实路径中导致主要功能错误、权限绕过、重复计费或高概率生产故障。
- P2：影响局部正确性、恢复能力、可维护性或用户操作，但不构成主要中断。

没有具体失败路径、变更行和可执行建议的问题不得发布。

## 6. 上下文管理

上下文管理不再对整段 diff 做前缀截断：

1. 分页取得全部 changed files、状态、hunk 和可评论行映射。
2. 先建立完整文件清单，再按风险、调用路径和测试关联排序。
3. 每个文件获得最低审查预算；大文件按合法 hunk 分片。
4. 只补充变更附近的 base/head 代码、调用方、接口和相关测试。
5. 每批生成候选问题，随后对候选执行针对性反证和去重。
6. 输出已检查文件数、总文件数、已检查 hunk、跳过项和原因。

有效输入预算按以下公式计算：

```text
effective_budget = min(
  repository_limit,
  backend_context_window - output_reserve - safety_reserve
)
```

单个分片不得超过有效预算的 25%，默认保留 20% 安全余量。二进制、生成产物、超大文件和敏感路径可跳过，但必须在覆盖报告中明确说明。

上下文键为 `仓库 + PR + Head SHA + 运行编号`。不同仓库、PR 和 Head 之间不得复用原始上下文。复审只携带触发评论、相关行线程、上一轮公开结论和结构化运行状态，不灌入整条历史。系统不保存代码全文、原始提示词、隐藏思维过程或密钥。

只有默认分支中的 `AGENTS.md` 和 `.github/qykw.toml` 可以影响当前任务规则；PR 内对这些文件的修改仅作为待审内容，不能扩大 qykw 权限。

## 7. 工具和修改模式隔离

模型只能返回符合 Schema 的计划、发现或补丁，不能直接发起 HTTP、Shell、Git 或 GitHub 调用。控制器将结构化请求映射到固定工具；未登记的能力一律拒绝。

### 7.1 审查模式

允许：

- 读取 PR 快照、文件、diff、评论和 CI 状态。
- 添加 `😄`。
- 创建或更新 qykw 状态总结。
- 发布 `COMMENT` 类型的行内问题。

审查任务绝不执行 PR 代码，也不持有代码发布令牌。

### 7.2 修改模式

修改流程采用三段隔离：

1. **补丁生成**：读取固定 base 和需求，生成受控补丁；持有推理凭据，不持有 GitHub 写令牌。
2. **无密钥验证**：在无 Secrets、无持久化 Git 凭据和无外网沙箱中应用补丁，只运行默认分支声明的命名测试方案。
3. **独立发布**：在干净 checkout 中重新校验补丁哈希和 base，创建 `qykw/...` 分支及 PR；持有写令牌，但不执行仓库代码。

模型不能提供任意测试命令。可信测试方案由默认分支配置，例如 `backend`、`frontend`、`full`。测试失败时不创建分支或 PR，只发布失败证据。

路径穿越、符号链接、二进制、大文件、子模块和敏感配置默认拒绝。修改 `.github/**`、`CODEOWNERS`、`.github/qykw.toml`、权限文件及 Secrets 引用必须拒绝。

## 8. 配置与凭据

`.github/qykw.toml` 只保存非敏感配置，并从默认分支读取：

```toml
version = 1
language = "zh-CN"

[authorization]
code_writers = ["xyh202131"]

[review]
auto_initial = true
auto_on_synchronize = false
max_findings = 20
run_timeout_seconds = 900

[context]
safety_reserve_ratio = 0.20
max_chunk_ratio = 0.25

[commands]
enabled = ["帮助", "分析", "计划", "审查", "复审", "状态", "总结", "修复", "实现", "停止"]

[verification]
required_checks = []
profiles = ["backend", "frontend", "full"]
```

密钥、端点、后台能力和模型仅通过受保护的 `QYKW_*` 环境配置提供。端点必须为 HTTPS 固定白名单，禁止跨源重定向、内网地址、用户信息和动态主机。公开日志和评论不得出现这些配置值。

审查、补丁生成、无密钥测试和发布分别使用最小能力的 job 与凭据。高权限令牌不得进入审查或测试环境。

## 9. 状态机与后台调用

运行状态：

```text
accepted → acknowledged → collecting → analyzing
→ validating → testing → publishing → completed
```

异常终态为 `partial`、`failed`、`canceled` 和 `stale`。每次运行生成编号，例如 `QY-PR53-A1B2`。状态保存于 qykw 自有隐藏标记和 Actions 产物，包括：触发事件、评论 ID、命令、授权人、Head SHA、提示词版本、阶段、覆盖率、取消标记和通用错误码。

同一评论 ID 或事件幂等键只能对应一个运行。显式复审不会清除“首次自动审查已完成”标记。分页查找状态和旧评论，不能假定前 100 条包含全部 qykw 记录。

后台请求包含运行编号、阶段、截止时间、输出上限和幂等键：

- DNS、TLS 和快速连接失败最多重试一次。
- 读取超时不盲目重试。
- 429 只在总截止时间允许时遵守服务端等待时间。
- 已可能被接收的写式推理请求不得因连接中断自动重复计费。
- 日志只记录请求编号、阶段、耗时、调用次数、Token 用量和通用错误码。

第一版“停止”为软取消：写入 `cancel_requested`，运行器在每个阶段、每次后台调用前后和发布前检查。界面不得声称已经瞬时终止仍在传输的请求。

发布前必须重新读取 Head SHA。Head 已变化时，运行进入 `stale`，不得发布旧行号评论；用户可使用 `@qykw 复审`启动新运行。

## 10. GitHub 输出契约

状态集中更新在一条总结评论中：

```markdown
## qykw 评审

结论：建议修改后合并
覆盖范围：18/18 个文件，42/42 个变更块
验证情况：单元测试通过，前端构建通过
问题统计：P0 0 / P1 1 / P2 2
限制：未运行端到端浏览器测试
运行：QY-PR53-A1B2 · abc1234
```

总体总结发布或更新后，每个有效问题对应一条变更行评论，包含：

- 问题编号与严重度。
- 实际影响。
- 可复现证据。
- 修改建议。
- 推荐验证方法。

零问题只能写“未发现有充分证据的问题”，不能批准 PR，也不能宣称代码绝对安全。发布器必须过滤伪造状态标记、HTML、图片、意外 `@mention` 和非可信外链。模型输出不能直接作为完整 Markdown 发布。

## 11. 错误与恢复

- Reaction 失败：记录警告并继续。
- 部分文件无法读取：进入 `partial`，列出遗漏和原因。
- 后台失败：保留阶段、错误分类、运行编号和可重试性。
- 总结成功而行评失败：保留总结，不覆盖成笼统失败；重试只补发缺失行评。
- 测试失败：不创建分支或 PR，输出失败命令名称、退出码和安全截断日志。
- 授权失效：发布前二次校验并停止写入。
- Head 漂移：进入 `stale`，不发布过期行评。
- 重复事件：返回现有运行，不重复调用和计费。

## 12. 安全边界

- 命令模式、权限和工具由确定性代码决定，模型不能扩权。
- 评论、diff、代码、链接和工具输出全部视为不可信输入。
- 审查凭据、推理凭据、测试环境和发布凭据严格分离。
- 测试环境无 Secrets、无持久化 Git 凭据、无外网，并设置时间、CPU、内存和输出上限。
- 出站端点执行 HTTPS、主机、DNS 解析和重定向校验。
- 日志不记录密钥、代码正文、完整评论、完整响应或敏感路径内容。
- 只信任登录名为 `qykw` 的状态标记和评论指纹。
- 发布前再次验证权限、Head、base、补丁哈希和目标分支。

## 14. 迁移顺序

1. 先增加首次触发、精确提及、权限、身份和状态机失败测试。
2. 建立 `tools/qykw/` 类型、接口、配置和纯函数命令路由。
3. 将旧入口临时委托给新运行器，保持已有审查能力可回退。
4. 上线独立提示词、分片上下文、覆盖率和两阶段问题验证。
5. 替换发布器和新的 qykw 状态标记；旧标记只读兼容，不再写入。
6. 更新审查工作流，移除后续 push 自动触发，保留可信默认分支 checkout。
7. 评审链路稳定并通过测试 PR 后，再启用隔离的“修复/实现”三段工作流。
8. 更新文档和配置示例，验证首次、Draft→Ready、复审、重复事件、失败恢复和 Head 漂移。
9. 删除旧入口、旧配置名、旧工作流和旧测试名称。

## 15. 完成定义

当且仅当以下条件同时满足，qykw 独立双通道升级才算完成：

- 所有确认的命令、权限和首次触发规则已实现。
- 公开身份、日志、状态和输出均只呈现 qykw。
- 审查完整覆盖并明确报告任何遗漏。
- 修改模式通过三段隔离，且只能创建等待人类审查的 PR。
- 安全测试、单元测试、集成测试和真实测试 PR 全部通过。
- 文档、配置、工作流和实际行为一致。
- 不存在占位配置、静默降级或未说明的自动写入路径。
